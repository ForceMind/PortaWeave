# ADR 0018 — Volatile cooperative descriptor range grants

Date: 2026-10-29. Status: core/native primitive, no system lock dispatch or mounted-volume certification.

Development-volume locking remains a release gate. Add an owner-serialized nonblocking coordination primitive on a live regular-file handle. Conflict identity is catalog inode, so separate opens through hard-link aliases conflict. Shared grants overlap; a different handle's overlapping exclusive grant conflicts. Ranges are finite unsigned half-open [offset, offset+length), may extend past current EOF, and reject zero length/overflow. Adjacent ranges do not overlap.

Each acquisition returns its own opaque process-local token. Overlapping acquisitions by the same handle coexist, including different modes; releasing one token does not convert, split, merge or remove other grants. These are explicit primitive semantics, NOT a complete fcntl/OFD/flock/LockFileEx implementation. No blocking wait, cancellation, deadlock detection, infinite EOF range, lock query, partial unlock, range conversion or OS process/dup/fork ownership is provided. The [GNU libc OFD discussion](https://sourceware.org/glibc/manual/2.25/html_node/Open-File-Description-Locks.html) distinguishes advisory coordination from OS ownership and replacement semantics; those full syscall contracts must be implemented independently in future adapters.

All administrative and policy acquisitions share a core per-owner 4096-grant admission limit. Scan is bounded by that count; it is not an exact heap budget. Reject before publishing a token or modifying grants. Conflict is a distinct LockConflict / additive PW_LOCK_CONFLICT=-20, not Busy, I/O or storage write protection. All previous ABI values and schemas/markers/capabilities remain unchanged. No lock is written to SQLite, transferred with container artifacts or restored on reopen.

PosixFile shared/exclusive requests need its previously granted READ/WRITE respectively, without a new pathname or mode check. Unlock needs the still-live originating handle and exact token. A separate open is a separate owner; copying the Rust capability identifies the same owner and closing it invalidates every copy. Closing any handle releases only its own grants before maintenance; release works under storage protection. Unlink/rename/chmod do not revoke open-time grants. Grants retain no additional inode or data reference; their existing file handle pins the inode.

The additive C policy API uses a separate lock-token table associated with its originating policy-file token. Validate all outputs/modes before acquiring. Reserve the native token before the core grant, then publish and write output; failed outputs stay unchanged. Wrong-volume, stale, wrong-file and cross-type tokens cannot release a lock. Policy close retires its native lock entries and the core handle's grants. Include locks in native BUSY; never silently evict or persist them.

These locks are cooperative: ordinary I/O, truncate, rename/unlink, mappings and immutable read leases do not consult them. They authenticate no OS identity, implement no Windows share modes or mandatory locks, and make no claim that mounted SQLite works. No WinFsp Open/security/Flush or FSKit access/load/mount gate is enabled. Actual system locks, native sharing, waiting/lifecycle semantics, cache/sync and developer workloads remain mandatory separate work.
