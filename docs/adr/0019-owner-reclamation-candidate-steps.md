# ADR 0019 — Reclamation candidate budgets on the existing owner

Date: 2026-11-03. Status: implemented increment; exact-source CI pending at authoring.

M1-Q independently bounds copied compaction payload. Orphan/dead-segment cleanup still materializes whole result sets, and no administrative continuation exists without another business mutation. Do not open a second SQLite connection/owner for a background collector.

Each existing post-business maintenance pass and the new explicit `Volume::maintenance_step` share the same implementation. Admit at most 128 orphan candidates, 128 dead-segment candidates in each of two phases, 128 mixed-segment candidates, and one compaction batch of at most 256 64-KiB blocks. Skipped pinned candidates consume admission. This bounds Rust candidate/result materialization and counted filesystem deletions/copy payload, **not SQL scans, joins, sort/cache memory, cascade-delete work, fsync latency, process-wide ABI lock latency or a hard wall-clock/heap budget**. One orphan deletion can cascade through many block rows atomically; do not partially delete its data and expose an old-size inode to administrative reopen.

Three process-local keyset sweeps retain `after` and a fixed maximum catalog ID for the current traversal. Concurrent legitimate requests remain serialized by the same owner; new higher IDs wait for the next sweep. The finite high-water mark prevents fresh IDs from indefinitely postponing wrap and reconsideration of lower pinned IDs. Partial compaction resumes its immutable source; failed/space-deferred compaction does not consume its selected candidate. These cursors are volatile scheduling hints, not a second persistent work log or authority. Reopen resets them, validates the exact known schema/current references first, and performs one bounded candidate pass; large abandoned backlogs need subsequent owner steps.

Deletion still follows the SQLite authority and active handle/lease tables. No old segment is retired before replacement durability, reference commit and reader retirement. v3's global invalid-orphan-directory guard remains; v1/v2 reject orphan directories as before. Formats/markers/default v1 and explicit v2/v3 creation/capabilities are unchanged, with no migration.

`MaintenanceReport` counts completed work on success. Zero work and `Healthy` do not prove an empty backlog; there is no drained flag. Foreground business success still survives later maintenance failure. An explicitly requested maintenance step instead returns its own error: HostSpace records DeferredSpace without poisoning; genuine maintenance failure records Failed and latches protection. Earlier cleanup phases may already have committed even when a later phase fails; the error is not a rollback promise.

The additive administrative C entry uses the existing serialized session and validates output admission before work. Failure preserves output bytes but does not erase actual cleanup progress. It retains every pin, lease/cursor table, BUSY close condition and capability distinction. Tokens do not authenticate OS users. A successful step is not fsync, safe eject or a system mount.

This provides continuation for an eventual owner idle event loop, **not an automatic timer/worker**. The native owner must later schedule, quiesce and cancel between steps; no hidden thread, independent database owner, driver installation or native access/Open/Flush/load/mount gate is enabled here. Complete SQL/resource and lifecycle budgets, WAL/vacuum, reservation and true mounted developer-volume gates remain open.
