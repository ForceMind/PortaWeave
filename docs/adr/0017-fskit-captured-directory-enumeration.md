# ADR 0017 — Captured FSKit directory metadata and explicit restart

Date: 2026-10-28. Status: experimental administrative core/native/SDK implementation, not an authorized system mount.

The SDK adapter cached names with the old administrative cursor, then queried each child's CURRENT stat/metadata during packing. A later write, unlink and final reclaim could pair an old name with different attributes or fail mid-page after the child inode was collected. Reusing that names-only cursor for a new initial enumeration also prevented a clean distinction between replay and observing the current directory.

Add an owned administrative ObjectDirectorySnapshot in the core: directory, optional logical parent, and ordered names WITH ObjectInfo, captured in one serialized owner observation. Bound children before materialization. v1 metadata remains None; v2/v3 stored metadata is explicit. Root's parent is root. An unlinked empty non-root directory has no parent/children. These copies admit no inode/data pin, no policy grant or future path authority. Current policy snapshots and raw administrative observations remain separate.

Add a distinct native FSKit metadata cursor table. Capture and project ALL names/attributes before reserving and publishing its process-local token. Native next/seek replay only those owned values, without catalog reads or lazy projection. Every refused/EOF output and position is unchanged, including small buffers. A bad ordinal on a valid cursor returns additive PW_BAD_COOKIE=-19; wrong/foreign/stale tokens remain INVALID. Existing ABI values, functions, formats/schema/capabilities and old cursor semantics are unchanged.

The new table shares 64 cursors and 100000 retained entries with legacy administrative and Windows tables. Include every synthetic dot row in that budget. Atomic replacement credits only its old entries/slot, prepares/project/reserves before retiring the old token, and targets the SAME captured directory ID. Refusal preserves the old token/position/data; success requires discarding old cookies. Old and prepared copies temporarily coexist; counts are not exact/peak heap or OOM guarantees. SDK pressure eviction can close only its own LRU metadata cursors, never its replacement target, foreign cursors or file/directory pins.

For FSKit only, an initial verifier=0/cookie=0 explicitly begins a NEW observation, atomically replacing its own retained snapshot when present. A nonzero verifier resumes immutable data and never refreshes merely because cookie=0. A successful new enumeration retires the prior verifier with ESTALE; a failed restart keeps it readable. Preserve the 32-entry SDK LRU and explicit stale errors. This supersedes M0-K's reuse of the same verifier for independent initial listings, while fixing the same leaked-cursor problem by replacement. WinFsp NULL Marker replay and its separate refresh APIs are unchanged.

Follow the fixed macOS26 [Operations enumeration contract](https://developer.apple.com/documentation/fskit/fsvolume/operations/enumeratedirectory%28_%3Astartingat%3Averifier%3Aattributes%3Apacker%3Areplyhandler%3A%29). Without requested attributes, linked/root FSKit snapshots contain `.` and `..` with the captured directory/logical-parent IDs; both root rows identify root. With attributes, omit dots. Never invent dots for a removed empty directory. Dot-mode changes cannot reuse old ordinal cookies. Map bad cookies to NSPOSIXErrorDomain plus FSError.Code.invalidDirectoryCookie. Packer rejection retains the last accepted cookie, so seeking that cookie retries its unaccepted row. Do not use macOS27 Handler/FSContext signatures or claim that a closure exercised kernel packer dispatch.

Validate frozen attributes after overwrite/unlink/final GC, fresh restart and failed restart, dot/parent/root/v1 rules, typed tokens, shared admission and real reader/replacement threads. Run actual C callers, SDK objects/closures, unsigned App/Extension build and the same artifact across OS runners. Keep native caller/security/Open/Flush and FSKit access/probe/load/activate/mount gates closed. Administrative metadata copies are not effective permissions, cache notification/coherence, OS mmap, real mount, Codex sandbox or exFAT/power-loss certification.
