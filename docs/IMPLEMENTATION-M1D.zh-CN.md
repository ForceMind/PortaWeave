# M1-D：按范围读取与读取租约索引预算

日期：2026-10-24。基于 `main` 的 M1-C 实验性存储格式开展的内存安全与大文件性能增量。**不改变容器格式，不是实际挂载，也不是 Codex 验收。**

## 为什么需要

原来的 `Volume::read` 和 `write` 每次操作都读取文件的全部块映射。即使只读一个很小的范围，文件拥有大量块时也会构造完整索引，存在不必要的内存与数据库遍历成本。原来的 `acquire_view` 还会复制全部映射，反复创建读取租约可能耗尽内存。

## 实现

- 普通 read 根据 offset 与实际可读取长度选择范围内的块映射；写入只选择被覆盖的块，部分尾块截断只查对应块。文件中没有分配的数据范围返回零，不用根据整个文件逻辑长度分配缓冲区；单次 I/O 原有 16 MiB 上限保持。
- 独立的 ReadView 要维护旧块引用，以保证覆盖/删除后还可以读取旧版本。目前不是范围级 COW 快照。新增 `ReadViewLimits`，默认单 owner 最多 128 个读取租约、全部租约索引合计最多 65,536 个块引用；根据 SQLite COUNT 预检后才分配快照索引。超限返回 `ResourceLimit`，不关闭或破坏已有租约，不使卷进入写保护。
- `set_read_view_limits` 只作用于当前 owner，不持久化；调低到少于仍存活的租约或索引需要量会被拒绝。释放租约后减少计数，不受后续数据写入导致的当前块布局改变影响。
- Stats 新增 `indexed_view_block_refs` 和 `read_view_limits`，展示这项有界账目。

## 真实边界

本次限制的是**索引条目数**，不是准确的堆内存字节数；Rust Vec、每项 checksum、SQLite 缓存和单次 I/O 缓冲都有额外开销。拥有超过条目上限的大文件暂时无法获得整个文件的 ReadView，但仍可经普通范围读取和写入接口访问；正常工作盘发布前必须补范围化租约或其他可扩展的一致性机制，不能将大文件阻断当成最终兼容性。

`read` 按范围查询的优化也不意味着全部 API 已经有全局内存预算：`verify`、`pinned_segments`、GC 候选索引、恢复导出等仍需要进一步界限。不能用此增量宣称大规模负载或任意文件大小通过。

## 测试门禁

新增 `crates/core/tests/read_views.rs`：
- 超过单 owner 活动租约数、累计块索引数时保持未写保护和原内容；
- 已存在租约时拒绝过小预算，释放后可以调整和重试；
- 覆盖及 unlink 时旧租约保留旧块，新文件操作返回新数据；释放后回收；
- 对非常大的稀疏逻辑文件做局部读/写，无需预分配逻辑长度。

只有对应 CI 实际完成后才能记录测试通过。三平台 CI 仅验证共享核心，不代替 exFAT 硬件、FSKit/WinFsp 真实挂载与本地 Codex 沙盒测试。
